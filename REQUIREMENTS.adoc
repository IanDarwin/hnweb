[#intro]
== Introduction

=== Purpose

`hnweb` is a web application that lets the executive of a small non-profit nature club keep track of
its membership: who belongs, what type of membership they have, when it expires, who has renewed and
how they paid, and how to contact them. It also publishes the club's upcoming meetings and lets
authorized people send e-mail to groups of members.

It was built for the Headwaters Nature club (Orangeville, Ontario, Canada), is configured by an
organization name, and is described in its README as a sample of Jakarta Persistence in a JSF environment.
The TODO list includes generalizing it for use by other clubs.

=== Scope

In scope:

* Member records, including family memberships and an archive ("deleted") state.
* Login, role-based access, self-service password set/reset.
* Annual membership renewal and a log of renewal transactions.
* Meeting/event listing and administration.
* Bulk e-mail to groups of members, with an optional attachment.
* CSV/text extracts of the member list; name-badge preparation (stub).
* Online signup without payment: a public form creates an unconfirmed record and e-mails a confirmation link (FR-100 to FR-104).
* Online renewal with card payment through Helcim (built; not yet exercised against the live service and not yet offered to members, FR-110 to FR-113).
* A membership statistics page for executives (FR-62).
* The older signup form with a small CGI backend (`SignupForm`, `membership-mailer`), if still deployed.
* Operator scripts for reporting and maintenance against the database.

Out of scope (not implemented at present): online payment of _new_ memberships, a self-service member profile editor,
and possibly multi-club (multi-tenant) operation.

=== Definitions

[horizontal]
Member:: A person with a row in the `Member` table whose discriminator `type` is `Member` (active).
Unconfirmed member:: A row whose `type` is `Unconfirmed` (class `UnconfirmedMember`): someone who filled in the signup form but has not yet clicked the e-mailed link. Not a member, not mailed, not counted.
Archived member:: A row whose `type` is `MemberArchived`. It is the same row, with the type flipped; see <<fr-archive>>.
Family master:: The `Family` (FM) member who pays for the family. Secondary members point at the master.
Secondary:: A `Secondary` (FS) member: an extra person on a family membership.
Membership year:: The year from 1 September to 31 August, named for the calendar year in which it _ends_ (September 2026 to August 2027 is "2027").
Expiry year:: The membership year through which a member is paid up. `0` means "never paid".
Executive ("exec"):: A member whose `position` field is non-empty (president, treasurer, and so on).
Admin:: A member with the `admin` role in the `member_roles` table.

[#overall]
== Overall description

=== Product perspective

A server-side Jakarta EE web application (WAR) deployed to a Jakarta EE application server (WildFly in the README).
Pages are Jakarta Faces (JSF) Facelets with PrimeFaces 13; persistence is JPA with Hibernate against a relational
database (PostgreSQL in operation, per the scripts and the driver in the build; in-memory H2 in tests).

[source]
----
                    +------------------------+
 Browser ---HTTPS-->| hnweb WAR (WildFly)    |-----JDBC------> database ("hn")
 (members,          |  JSF pages *.web,*.xhtml|
  executives,       |  PageFilter (auth)     |-----SMTP------> mail server
  admins)           |  JAX-RS /api/...       |                 (java:jboss/mail/Default)
                    +------------------------+
 Browser ---HTTPS---> HelcimPay.js (card entry; card data never reaches hnweb)
 Browser ---POST /signup---> membership-mailer (older C/kcgi CGI; superseded by Signup1) ---SMTP---> club admin
 Operator ---ssh/psql---> scripts/*  (reports, bulk fixes)
----

=== User classes

[cols="1,3,3"]
|===
|Class |How identified |What they may do

|Visitor (anonymous)
|No login.
|See the home page and upcoming events; view an event's details; read About and Privacy; sign up online (`Signup1`) and confirm by e-mailed link; see the paper signup form;
set or reset their own password by e-mail token; log in.

|Member
|Logged in (any `Member` row with a password).
|Everything a visitor can. Can renew online by card (`Renew`, built but deferred). Intended (not yet delivered) to update their own record.

|Executive
|Logged in, with a non-empty `position`; also granted the synthetic role `exec`.
|View the member list and archived list, view any member, export CSV lists, send bulk e-mail, see the events list.

|Admin
|Logged in, with role `admin` in `member_roles`.
|Everything an executive can, plus create/edit/archive/restore members, renew memberships, administer events and
the transaction log, and prepare name badges.
|===

NOTE: The README tells deployers to create a user "in the role of `club_exec`", but the code checks the roles
`admin` and the synthetic `exec` only. See xref:ISSUES.adoc#gap-roles[ISSUES].

=== Operating environment and constraints

* Jakarta EE 11 API, Java 17 or later, JSF/Facelets with PrimeFaces 13 (theme "saga"), Hibernate ORM 7.
* Application server supplies the JTA datasource `java:jboss/datasources/HnClubDataSource` and the mail session `java:jboss/mail/Default`.
* All pages are served through the Faces servlet mapped to `*.web` and `*.xhtml` (the latter so that page source is never served as text; see xref:ISSUES.adoc#gap-xhtml-filter[ISSUES]). Staff pages live under `/admin/`; request and response encoding is UTF-8.
* `config.properties` (on the classpath) supplies the organization name, mail settings, the renewal month, the site base URL, and the optional online-payment settings (see <<ir-config>>).
* The membership year is fixed at 1 September to 31 August by default; the renewal month is a property (`datetime.renewalmonth`, default 9).
* Canadian context: provinces are the Canadian provinces and territories; amounts on the signup form are in Canadian dollars.

=== Assumptions

* An e-mail address uniquely identifies a member for the purposes of login and password reset (nothing enforces this; see xref:ISSUES.adoc#gap-email-unique[ISSUES]).
* The club is small enough (hundreds of members) that lists are loaded whole and filtered in memory, and tables are not paged.
* Executives and admins are trusted with all members' personal data.

[cols="1,6,1"]
|===
|ID |Requirement |Status

|FR-10

|FR-12

|FR-13

|FR-14

|Done

|FR-15
|Every failure on step 2 (blank input, weak password, unknown, expired or already-used token, no unique member) shall return to step 2 with one generic message (`?error=token`); no JPA or internal detail is shown.
|Done

|FR-16
|On success the member's stored password shall be replaced by the hash of the new password, and the member shall land on `ChangePassword3` ("We've made the password change you requested").

[#fr-signup]
=== Online signup (no payment)

A visitor signs up on `Signup1`. The person is stored in the `member` table as an `UnconfirmedMember` (discriminator `Unconfirmed`) and becomes a `Member` only when the e-mailed link is followed.

[cols="1,6,1"]
|===
|ID |Requirement |Status

|FR-100
|`Signup1` shall collect first and last name, e-mail address, city, province, country and phone, and the chosen membership type (individual or family). Fees are shown in the type selector.
|Done (fees are written into the page)

|FR-101
|On submission, `SignupService.begin` shall: reject an address that already belongs to a member (the visitor is told so, and no mail is sent); remove earlier unconfirmed attempts for the same address with a single bulk delete restricted by the entity's discriminator (so it cannot remove a confirmed member, even if the person confirms in the meantime); store a new `UnconfirmedMember`; create a signup token; and e-mail a link containing the token.
|Done (`SignupServiceTest`)

|FR-102
|A signup token shall be 24 random bytes encoded URL-safe (32 characters), valid for 72 hours and for a single use. It lives in the same `pwchangetoken` table as password-reset tokens, distinguished by the `purpose` column (unset means password reset). It is consumed as soon as it is found, even if expired.
|Done

|FR-103
|Following the link (`Signup2?token=...`, handled by `f:viewParam` and `f:viewAction`) shall flip the row from `Unconfirmed` to `Member` (native SQL, `MemberDAO.flipMemberType`), leaving the expiry year at 0 (not paid up) and recording no transaction, and redirect to `SignupDone`. A bad, expired or used token shall show a clear message.
|Done (confirmed by manual testing; a confirmed signup is unpaid until an admin renews them; see xref:ISSUES.adoc#gap-signup-unpaid[ISSUES])

|FR-104
|If the confirmation e-mail cannot be sent, the visitor shall be told so, and the signup shall not be left half-made.
|Done (`MailMan` throws `MailSendException`; the transaction rolls back)
|===

NOTE: Signup collects no payment. The new member pays the treasurer by cheque or e-transfer, and an admin records it with `admin/Renew`, which sets the first expiry year and records the transaction.

[#fr-renew-online]
=== Online renewal and payment (built, deferred)

[cols="1,6,1"]
|===
|ID |Requirement |Status

|FR-110
|A logged-in member shall be able to renew on `Renew` (top level): choose 1 to 3 years; the fee is `renewal.fee.<type>` per year in `renewal.currency`. A member type with no configured fee cannot renew online. Secondaries are renewed through their master.
|Done (not exercised live)

|FR-111
|Payment shall use HelcimPay.js: the server calls Helcim's initialize endpoint (`HelcimClient`) and receives a `checkoutToken` and `secretToken`; the browser (`js/helcim-renew.js`) opens the card dialog, so card data goes to Helcim and never to hnweb. The page receives the success result through a hidden field and a hidden button.
|Done (not exercised live)

|FR-112
|Before renewing, the server shall validate the result: the SHA-256 of the compact transaction data plus the secret token must match the hash Helcim sent (both the ASCII-escaped and unescaped JSON spellings are tried); status `APPROVED`; type `purchase`; amount and currency as expected; and the transaction id unused. On success `RenewalService` renews the member per <<br-renew>>, records a `MemberTransaction` of payment type credit card with `externalRef` `helcim:<id>` (unique, so a repeated submission is refused), and shows the new expiry.
|Done (`HelcimClientTest`; not exercised live)

|FR-113

[#business]
== Business rules

[#br-year]
=== Membership year

[horizontal]
BR-01:: The membership year runs 1 September to 31 August and is named for the year it ends. In or after the renewal month (default September) the current membership year is the _next_ calendar year; before it, the current calendar year.
BR-02:: A member joining today has an expiry year equal to the current membership year, except that someone joining in or after the renewal month gets `year + 1` (the same thing, restated in `getNewMemberExpiryYear`).
BR-03:: A member is *expired* when the calendar year is past their expiry year, or when it is the expiry year and the month is after the renewal month (so there is a one-month grace period: a member with expiry year 2026 is still current through September 2026). A secondary is expired when their master is.

[#br-renew]
=== Renewal

[horizontal]
BR-04:: A renewal of _n_ years sets the new expiry year to `max(current expiry year, current membership year - 1) + n`.
BR-05:: Consequence: a member who has lapsed gets one year bought as "the current membership year", not as an extension from their old expiry (for example, a member who expired in 2026, renewing for one year in October 2026, is paid through 2027); a member who is paid ahead keeps the years they have already paid.

.Worked examples (from `YearCalcsTest`)
[cols="1,1,1,1,1"]
|===
|Today |Expiry before |Years |Expiry after |Why

|2026-10 |2026 |1 |2027 |lapsed: current year is 2027
|2026-10 |2020 |1 |2027 |long lapsed: starts from now
|2026-10 |2026 |2 |2028 |
|2026-10 |2027 |1 |2028 |paid ahead: extend
|2026-10 |2029 |1 |2030 |paid ahead: keep extra years
|2026-03 |2025 |1 |2026 |before September the current year is 2026
|===

[horizontal]
BR-06:: Payments are cash, cheque or Interac e-transfer when an admin renews; a member who renews online pays by credit card through Helcim; the system also knows debit card and unknown. Credit card numbers are never stored.
BR-07:: A person is either an Individual, Family master, Family Secondary, Student, or Mail-Only (not a member; on the mailing list only). Expiry is not meaningful for Mail-Only people (not enforced; with expiry 0 they are never "paid-up").

[#br-mail]
=== Who gets which mailing

[cols="1,4"]
|===
|Mailing |Recipients

|Test |The sender only.
|Executive |Active members with a non-empty `position`.
|Paid-up |Active members whose expiry year's 31 August is still in the future.
|Entire list |Every active member with an e-mail address, current and former.
|Expired ("nags") |Active members whose expiry year is before the current calendar year.
|===

NOTE: The "paid-up" and "expired" rules use different definitions of the year. See xref:ISSUES.adoc#gap-mail-rules[ISSUES].

[#br-access]
=== Access and privacy

[horizontal]
BR-08:: Only executives and admins may see other members' personal information (the Privacy page promises this).
BR-09:: Only admins may change data (create, edit, archive, renew, events, transactions). Executives are read-only, but see xref:ISSUES.adoc#gap-undelete-role[ISSUES].
BR-10:: The club stores name, city, e-mail and phone numbers. It states that it no longer stores street addresses and never stores credit card numbers.
BR-11:: Passwords are stored as hashes, never in the clear.
BR-12:: An unconfirmed signup is not a member: it is excluded from every list, statistic and mailing, and cannot log in.

=== Data rules

[horizontal]
DR-01:: An archived member keeps every field, including the link to their master, so restoring is lossless.
DR-02:: Member identity is the database id. Two member objects are equal only if both have an id and the ids match.
DR-03:: Only `Member` rows carry roles and the secondaries set in the object model; the master link is readable on every row through `masterMemberId`.
DR-06:: Converting between `Member`, `MemberArchived` and `Unconfirmed` is done by native SQL on the `type` column (`MemberDAO.flipMemberType`), because JPA cannot change an entity's class.
DR-07:: E-mail addresses are declared unique in the mapping. Databases created before the declaration need the constraint added by hand (see xref:ISSUES.adoc#gap-email-unique[ISSUES]).
DR-04:: Dates are stored without time zone; event times are stored as text in "HH:mm" form.
DR-05:: The schema is created and updated automatically at deployment (`schema-generation: update`), so a new deployment needs no hand-run DDL after the first run. The test persistence unit starts empty (no load script).

[#interfaces]
== External interfaces

[horizontal]
IR-01:: *Database.* A JTA datasource named `HnClubDataSource`. Hibernate is the JPA provider. Tests use in-memory H2.
IR-02:: *Mail.* The Jakarta Mail session `java:jboss/mail/Default`. Properties in `config.properties`: `mail.smtp.host`, `mail.smtp.from` (no-reply address), `mail.subject.prefix`, `mail.unsubscribe`.
IR-03:: *REST.* `POST /api/changePassword1` (form field `email`) and `POST /api/changePassword2` (form fields `token`, `newPassword`). Both answer with an HTTP 303 redirect to a `.web` page, built from the request's own `UriInfo` (no host name is hard-coded); there are no JSON endpoints.
IR-04:: *Signup CGI (legacy).* `POST /signup` handled by the separate C program `membership-mailer` (kcgi). No longer used by the web application.
[#ir-config]
IR-05:: *Configuration.* `config.properties` (the sample is `config.properties.sample`; the live copy is not committed). Keys the code reads: `orgName`, `mail.smtp.host`, `mail.smtp.from`, `mail.subject.prefix`, `mail.unsubscribe`, `datetime.renewalmonth`, `stats_note`, `site.baseurl` (base of links in e-mails), `signup.notify` (optional address told of each confirmed signup), and, for online renewal, `helcim.apitoken`, `helcim.apiurl` (optional override, for testing), `renewal.currency`, and `renewal.fee.<membertype>`. The sample also lists `url.base`, `url-mainsite` and `url-fbgroup`, which nothing reads (see xref:ISSUES.adoc#gap-sample-config[ISSUES]). For the test and link-crawl tools, `Config` also supplies `base`, `adminemail` and `adminpw`.
IR-06:: *Operator scripts.* Shell and awk scripts in `scripts/` talk to the PostgreSQL database `hn` directly with `psql` (see <<ops>>).
IR-07:: *Helcim.* HTTPS calls from `HelcimClient` to the Helcim API (initialize checkout) and the HelcimPay.js script in the browser; see FR-111.
IR-08:: *E-mail links.* The signup and password messages contain links built from `site.baseurl`; the person must be able to reach that address.

[#nfr]
== Non-functional requirements

[horizontal]
NFR-01 (Security):: All data-changing and personal-data pages require login and a role (FR-06). Session timeout is 2 hours. Password reset uses unguessable single-use tokens (FR-14) and a uniform error for every failure (FR-15).
NFR-02 (Security):: Passwords are stored as unsalted MD5. See xref:ISSUES.adoc#gap-md5[ISSUES].
NFR-03 (Privacy):: Credit card data is never stored; the Privacy page states what is kept and who sees it.
NFR-04 (Usability):: A single modern, responsive layout (stylesheet `css/stylesheet.css`); forms show inline field messages; destructive actions ask for confirmation; the password page gives live feedback.
NFR-05 (Internationalization):: Text is English only. Character encoding is UTF-8 end to end (request, response, and outgoing mail).
NFR-06 (Deployability):: One WAR plus a datasource, a mail session and `config.properties`. README steps are acknowledged to be "nowhere near user-friendly". Moving to a stand-alone Quarkus service on port 8500 is a stated goal (`TODO.txt`).
NFR-07 (Maintainability):: Per-page access rules live in small `page.xml` files rather than in code; business rules for dates are isolated in `YearCalcs`.
NFR-08 (Testability):: Unit and integration tests run against H2 with no server (see Appendix C), including full password-reset and signup flows with an in-JVM SMTP server (GreenMail). A separate integration test (`HttpLinkCrawlIT`, profile `it`) crawls a _deployed_ server with an HTTP client and reports broken links and error pages; browser-driven testing (Playwright, Selenium) was tried and abandoned because it does not work on OpenBSD.
NFR-09 (Performance):: No stated target. Lists are loaded in full and filtered in memory.
NFR-10 (Availability / data safety):: No explicit requirement. Archiving rather than deleting is the main safeguard against accidental loss.
